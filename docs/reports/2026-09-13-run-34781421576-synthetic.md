# Synthetic benchmark report: run 34781421576

Run [`34781421576`](https://github.com/starslingdev/hpc-sandbox-benchmarks/actions/runs/34781421576) · commit [`08dfc6eb`](https://github.com/starslingdev/hpc-sandbox-benchmarks/commit/08dfc6eb132dee567352ffa97abb96daa4db3153) · dispatched 2026-09-13 20:38 UTC · synthetic wave finished 21:21 UTC · report written 2026-09-13 while the realworld wave was still executing.

Scope: the **synthetic wave only** (`cpu-node`, `disk`, `memory`, `network`, `pgbench`, `system`), 12 providers, 3 replicate sandboxes per provider × suite, 2 fixed PTS passes per case. Target for every sandbox: **4 vCPU · 8 GiB RAM · 40 GB disk**. The realworld wave and the committed dataset for this run were not available when this was written; nothing here is a realworld number.

Every value below is the repo's own statistic: the **median of the per-sandbox medians** (one machine, one vote), with a seeded cluster bootstrap interval, computed by `buildLeaderboard` over a Run aggregated from the 216 attempt artifacts with `aggregateRuns`. The tables will match the committed dataset for these metrics once the run publishes; see [How these numbers were produced](#how-these-numbers-were-produced).

## Summary

- **Daytona (VM) is the most consistently fast synthetic environment.** It leads CPU (Node.js web tooling), memory (STREAM Triad, 178.6 GB/s, 1.66× the runner-up) and SQLite, is second on PyBench and Git, third on buffered 4K random read, and leaves the top four on only one of 26 metrics (pgbench read-write, 6th). Its numbers are also the most repeatable in the run: sandbox-to-sandbox spread under 1% on STREAM, PyBench, Git, SQLite.
- **Blaxel is the closest all-rounder** (mean rank 2.85 vs Daytona's 2.54): top three on 21 of 26 metrics, first on buffered 4K random write (292 k IOPS) and effectively tied with tama for first on pgbench read-only (338 k TPS vs 347 k, well inside tama's sandbox spread).
- **Novita leads network loopback by a wide margin** (157.5 Gbit/s single-stream TCP, 1.66× Blaxel) and pgbench read-write (26.9 k TPS), and is within 1% of Daytona on CPU. Its weak axis is disk: 9th on buffered random read (4.3× off the leader).
- **Namespace is bimodal across dimensions**: first on PyBench, Git and buffered 4K random read, last on STREAM (32.4 GB/s, 5.5× off Daytona). The Git result is 23.6% faster than the published leaderboard run.
- **Modal (gVisor) finishes in the bottom three on 14 of 26 metrics** and shows the largest gaps in the run: pgbench read-only at 13.9 k TPS is 25× below the leader, SQLite 472 s is 15× slower than Daytona, loopback UDP at the 10 Gbit objective reaches 160 Mbit/s where every KVM stack saturates at 9 999. This is a regression against the published leaderboard run (pgbench RO -80%, CPU -41%) that was already present in the intermediate run 34437329093.
- **Runloop is the slowest compute** (mean rank 10.3; last on CPU, PyBench and STREAM Copy; bottom three on 22 of 26 metrics) at the highest disclosed price in the run (0.634 USD/hr).
- **Disk changed meaning in this run.** Commit `ff75e64` (#459) pins the disk suite to buffered fio, so the catalog headline (4 KB random read, O_DIRECT) was not emitted by any provider and the fio rows are page-cache-inclusive. They are not comparable to the O_DIRECT rows in the published leaderboard; only Hardlink throughput carries over. Buffered results favour whichever stack serves reads from guest memory: Modal (gVisor) posts 18.25 GB/s sequential read, first in the run.
- **Two cells failed**: tama's network replicates 1 and 2 never allocated (`tama new ... failed to provision`), so tama's network row rests on one sandbox. tama also fails the compute-match check (probe sees the 96 vCPU / 1.5 TiB host); its ranks are flagged ⚠ and are not like-for-like.
- **No rank in this report is statistically separated.** With three sandboxes a side the exact Mann-Whitney floor is p = 0.10, above α = 0.05, so every row is "underpowered" by the repo's own test. Read the ratios and the per-sandbox medians, not the rank digits.

## Disk

**Read this section as page-cache-inclusive I/O.** Every fio row here is the `Direct: No` catalog variant. Commit `ff75e64` (2026-09-12, "align disk plans with buffered fio execution", #459) pins the suite command to `BENCH_FIO_DIRECT=No mise run benchmark:disk:all`, because earlier plans expected both modes while each sandbox ran only one, which made a complete disk comparison impossible. Consequences for this run:

- The catalog's disk headline (fio 4 KB random read, O_DIRECT, IOPS) has no rows. A leaderboard rendered from this run will lead the disk section with the first buffered metric instead.
- The fio deltas against the published leaderboard are undefined (different metric ids). Only Hardlink throughput is comparable across runs.
- Buffered 4 KB reads mostly measure the guest page cache and the syscall path; buffered 1 MB sequential reads with a 1 GB file can be served entirely from memory. That is why Modal (gVisor), last on most compute metrics, is first on sequential read at 18.25 GB/s, and why Namespace leads random read at 69.9 k IOPS while sitting last on STREAM.

What the buffered numbers still show:

- **Random 4 KB read**: Namespace 69.9 k IOPS, Blaxel 54.4 k, Daytona 47.6 k. tama (6.7 k) and Runloop (7.0 k) are 10× off the leader; E2B is 5.5× off.
- **Random 4 KB write**: Blaxel 292 k IOPS, Novita 248 k, Microsandbox Cloud 212 k. Modal (gVisor) writes at 24 k IOPS, 12× behind. E2B's three sandboxes returned 60 050, 60 100 and 60 050 IOPS (spread 0.0%), and its sequential rows are equally flat (600 / 599 / 600 IOPS read, 604 / 597 / 605 write). A spread that tight across three independent machines is the signature of a rate limit, not of a disk.
- **Sequential 1 MB read**: Modal (gVisor) 18.25 GB/s, Daytona 11.65 GB/s, Blaxel 9.73 GB/s; E2B 631 MB/s (29× off).
- **Sequential 1 MB write**: Daytona 5.21 GB/s, Namespace 4.46 GB/s, Blaxel 3.33 GB/s; E2B 635 MB/s and tama 533 MB/s at the bottom.
- **Hardlink throughput** (metadata-heavy, the one disk metric comparable across runs): Daytona 25.2 bogo ops/s, Blaxel 20.3, then a step down to Runloop and Novita at 12.2. E2B at 1.83 is 13.8× off the leader, and Modal (gVisor) at 3.0 is 8.4× off. The top two are unchanged from the published run; Runloop moved up from fifth to third and E2B improved 31% from a very low base.

run.cloud's disk rows have 31–36% sandbox spread on every fio metric because replicate 0 measured about half of the other two on reads and writes alike. That sandbox ran kernel 6.18.36 like the fastest one; the kernel 6.1.176 sandbox was the middle value, so the mix does not explain the split.

## Memory

Three providers have a sandbox that measured a different machine class:

For each of those the median lands on the slow pair, so the ranked value is the conservative one, but the upper bootstrap bound (tama 165.6, run.cloud 80.4, Microsandbox 96.8) shows what the fast host does.

Modal (gVisor) is also down 46–50% on all three loopback rows against the published run.

**WAN** numbers are path-dependent and noisy, and should be read with the egress table below. ## How these numbers were produced

Artifacts were fetched from the run with the GitHub API (`experiment-plan-34781421576` plus the 216 `experiment-attempt-34781421576-*` artifacts whose suite is not `realworld-*`), unpacked, and aggregated with the repo's own CLI at commit `08dfc6eb`:

```bash
bun apps/cli/src/bin/aggregate.ts 34781421576 <candidate-dir> <attempts>/*/run.json
bun apps/cli/src/bin/leaderboard.ts <candidate-dir>/runs/34781421576.json > leaderboard-34781421576-synthetic.md
```

`aggregate.ts` merges the per-cell shard Runs exactly as `commit-dataset.yml` will (`aggregateRuns`), including the two failed tama shards as recorded gaps. `leaderboard.ts` then applies `buildLeaderboard`: per-sandbox medians, seeded cluster bootstrap (10 000 resamples), exact Mann-Whitney U on per-sandbox medians, KS alongside. The ratio-to-best, sandbox-spread and delta columns in this report were computed on top of that output; the value, interval, sandbox and trial columns are the renderer's own. The published dataset will additionally contain the realworld metrics and any economics rows derived from them; the synthetic rows will be identical because the aggregation is deterministic over the same shards.

Not done here: `aggregate-experiment.ts` (the publication path) was not run, because it requires all 648 cells of the frozen plan and the realworld wave was still executing.
